# Bluetooth Cryptography & Endianness Conversions

This document explains the differences between Bluetooth Classic and Low Energy (LE) cryptographic keys, and why specific data conversions (like byte reversal and number base conversions) are necessary when transferring pairing states between Windows and Linux.

---

## Bluetooth Classic vs. Bluetooth Low Energy (LE)

The pairing mechanics differ significantly between the original Bluetooth Classic specification and the newer Bluetooth Low Energy (LE) specification.

### 1. Bluetooth Classic
*   **Pairing Type**: Security Manager (SM) legacy pairing or Secure Simple Pairing (SSP).
*   **Key Type**: A single **Link Key** (128-bit).
*   **Storage**: Both devices save this shared secret key.
*   **Sync Complexity**: Low. Simply copying the 16-byte hex representation from the Windows Registry to BlueZ's `[LinkKey]` section is sufficient.

### 2. Bluetooth Low Energy (LE)
*   **Pairing Type**: LE Legacy Pairing or LE Secure Connections.
*   **Key Type**: Multiple keys, primarily the **Long Term Key (LTK)**, **Identity Resolving Key (IRK)**, and **Connection Signature Resolving Key (CSRK)**.
*   **Storage**: Keys are accompanied by pairing parameters: the **Encrypted Diversifier (EDiv)** and **Randomizer (Rand)**.
*   **Sync Complexity**: High. The devices use `EDiv` and `Rand` as indexing parameters to retrieve the LTK during connection re-establishment. Windows and Linux format these parameters differently.

---

## The Endianness and Base Conversion Problem

When Windows registers a Bluetooth Low Energy device, it stores the pairing keys as raw registry types. BlueZ, on the other hand, expects these parameters in an INI text format with specific number bases and byte ordering (endianness).

### 1. Encrypted Diversifier (`EDIV` / `EDiv`)
*   **Definition**: A 16-bit integer (2 bytes) used to identify the LTK.
*   **Windows Registry**: Stored as a 4-byte `REG_DWORD` (little-endian hex format, e.g. `dword:000002ab` -> `0x02AB` in big-endian representation).
*   **BlueZ Info**: Expects a **decimal integer** (e.g. `683`).
*   **Conversion**: Convert the hexadecimal value directly to decimal. No byte reversal is needed for `EDIV` because Windows `REG_DWORD` type is parsed automatically by registry export as a 32-bit big-endian value in the text export file (`dword:000002ab` is `0x02AB` = `683`).

### 2. Randomizer (`ERand` / `Rand`)
*   **Definition**: A 64-bit random number (8 bytes) generated by the peripheral during bonding.
*   **Windows Registry**: Stored as a raw binary array (`REG_BINARY`) under the name `ERand`.
    *   *Example in registry file*: `hex:ab,cd,ef,12,34,56,78,90`
    *   This is stored in **little-endian** byte order, meaning the Least Significant Byte (LSB) is written first.
*   **BlueZ Info**: Expects a **decimal integer** of the full 64-bit value in **big-endian** order.
    *   *Expected in info*: `Rand=10411030018809425323`

#### The Conversion Process:
To map Windows `ERand` to BlueZ `Rand`, we must perform a **Byte Reversal** followed by a **Hex-to-Decimal** conversion:

```
1. Extract Registry ERand Bytes:
   [ AB, CD, EF, 12, 34, 56, 78, 90 ]

2. Reverse the Bytes (Little-Endian to Big-Endian):
   [ 90, 78, 56, 34, 12, EF, CD, AB ]

3. Form Big-Endian Hex String:
   "9078563412EFCDAB"

4. Convert to 64-bit Unsigned Decimal String:
   10411030018809425323
```

This tool automates this conversion inside `Export-BluetoothKeys.ps1` so that the generated `btkeys.json` file is fully pre-compiled and ready for the Linux import script to read without further arithmetic.
